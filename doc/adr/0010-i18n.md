# ADR 0010 — 다국어: URL이 아닌 쿠키

- 상태: 채택
- 날짜: 2026-09-12

## 배경

관리 화면은 한국어로 작성되었다. 한국어를 읽지 못하는 사람도 평가·운영할 수 있도록
영어를 지원하되, 이미 배포된 링크와 테스트를 깨뜨리지 않아야 한다.

## 결정

`locale` 쿠키로 언어를 전환한다. **URL은 바꾸지 않는다.**

- 사전은 `lib/i18n/dictionaries.ts` 에 한국어를 원본으로 두고, 영어는 그 타입을
  그대로 따른다. 키가 어긋나면 런타임 `undefined` 가 아니라 **타입 오류**가 난다.
- 서버 컴포넌트가 `getTranslations()` 로 사전을 읽어 클라이언트 컴포넌트에 내려준다.
- API 오류 메시지도 같은 사전을 쓴다. 다만 `code` 는 영문 enum으로 고정이다 —
  API 소비자는 문구가 아니라 코드에 의존해야 한다.
- **공개 폼은 한국어 고정**이다. 운영자의 언어 설정이 방문자 화면에 새면 안 된다.

## 결과

- `/ko/admin` 같은 경로 세그먼트를 도입했다면 모든 라우트 파일, 모든 테스트, 이미
  배포된 데모 링크가 함께 바뀐다. 운영자 한 명의 표시 언어를 위해 치르기에는 큰 비용이다.
- 언어는 서버에서 결정되므로 첫 렌더부터 올바른 언어가 나온다. 깜빡임이 없다.
- 전환 시 `router.refresh()` 가 필요하다. 번역문을 서버 컴포넌트가 들고 있기 때문이다.
- 검색엔진이 언어별로 색인할 수 없다. 관리 화면은 로그인 뒤에 있으므로 무의미하다.
- 사전 테스트가 두 로케일의 **키 집합과 `{placeholder}` 집합이 일치하는지** 검사한다.
  `{count}` 가 번역 과정에서 `{total}` 로 바뀌면 조용히 깨지는 대신 테스트가 실패한다.

## 검토한 대안

- **next-intl + `[locale]` 라우팅** — 표준적이고 SEO에 유리하지만, 위의 비용을 치를
  만한 이득이 이 앱에는 없다.
- **클라이언트 전용 번역(localStorage)** — 첫 렌더가 항상 기본 언어로 나와 깜빡인다.
- **`Accept-Language` 자동 감지** — 명시적 선택을 덮어쓸 수 있어 전환 버튼과 충돌한다.
